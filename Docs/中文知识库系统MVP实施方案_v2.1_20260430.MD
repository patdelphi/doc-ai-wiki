# 中文知识库与 AI 质检系统 MVP 实施方案

> **版本**：v2.1 MVP
> **日期**：2026-04-30
> **状态**：可执行实施版
> **说明**：本方案在保留原始目标架构的前提下，优先收敛首版能力边界，降低实现风险、成本波动和维护复杂度。

---

## 一、方案结论

本项目适合分阶段建设，定位为`通用中文知识库`，兼容少量古文内容与医学领域内容。

原 v2.0 方案的总体方向正确，但首版同时引入知识图谱、长窗口全量注入、多模型投票、复杂路由等能力，存在以下问题：

- 首版开发范围过大，难以在短周期内稳定交付
- 对云端长上下文和多模型链路依赖过强，成本和时延不稳定
- 图谱抽取质量、实体归一、版本差异处理尚未收敛，容易形成高复杂度低收益模块
- 缺少评测闭环，后续难以判断优化是否有效

因此，首版应采用“**先跑通主链路，再逐步增强**”的策略。

---

## 二、MVP 目标

### 2.1 首版只解决 4 个问题

1. 导入已有中文 Markdown 文档，并稳定完成入库
2. 能基于全文检索与语义检索找到相关证据片段
3. 能对输入文本按 claim 拆分并给出带出处的质检结果
4. 能让人工审核和沉淀质检记录

### 2.2 首版明确不做

以下能力不进入 MVP 首批开发范围，只保留接口或扩展位：

- 完整知识图谱推理
- 长窗口整篇文档全量注入作为默认路径
- 多模型投票常态化启用
- 图谱可视化
- 多版本文档自动差异分析
- 批量质检
- 对外开放 API
- 高风险专业辅助推荐

---

## 三、MVP 系统边界

### 3.1 输入边界

- 文档输入：优先支持**中文 Markdown 文档**
- 文本输入：单次质检文本建议控制在 **2000 字以内**
- 使用场景：优先支持“内容审核”“知识查证”“引用核验”

### 3.2 输出边界

系统输出仅用于：

- 中文知识内容检索
- 文本事实核验辅助
- 引文出处对照
- 人工审核辅助

系统输出**不得直接替代高风险专业判断**。

### 3.3 高风险内容约束

- 所有高风险结论必须展示证据来源
- 无证据时不得输出 `verified`
- 低置信度结果默认进入人工复核
- 涉及医学、法规、剂量、禁忌等高风险领域时，优先走确定性规则校验

## 四、MVP 架构

```text
前端界面
  ├─ 文档上传
  ├─ 文档检索
  ├─ AI 质检台
  └─ 审核记录

服务层
  ├─ 文档导入模块
  ├─ Markdown 清洗模块
  ├─ 分块与索引模块
  ├─ 检索融合模块
  ├─ claim 拆分与质检模块
  ├─ 规则引擎模块
  └─ 审核记录模块

存储层
  ├─ Markdown 文件
  ├─ SQLite（元数据、全文索引、审核记录）
  └─ ChromaDB（向量索引）
```

### 4.1 MVP 技术选型

| 层级 | 组件 | MVP 选型 | 说明 |
|------|------|----------|------|
| 前端 | 自用管理台 | Gradio | 首版开发最快，适合内部工具 |
| 服务 | Web API | FastAPI | 负责上传、检索、质检、审核接口 |
| 文档导入 | 输入格式 | Markdown | 当前阶段直接从已准备好的 Markdown 入库 |
| 文本清洗 | 轻量 LLM 精校 | Qwen-Max | 只用于必要修复、结构补全和疑难断句，不全量依赖 |
| 向量检索 | Embedding | 通义 text-embedding-v3 | 中文性价比高 |
| 向量索引 | 向量库 | ChromaDB | 嵌入式、低运维 |
| 全文检索 | 检索引擎 | SQLite FTS5 | 精确术语召回 |
| 质检分析 | 主模型 | Qwen-Max / Claude Sonnet | 按场景选择 |
| 规则引擎 | 本地规则 | Python + YAML | 确定性校验 |
| 数据存储 | 元数据与审核 | SQLite | 统一落库 |

### 4.2 首版不引入的基础设施

- Neo4j
- Milvus
- 独立消息队列
- 分布式任务系统
- 本地大模型
- 多活模型编排平台

## 五、核心链路设计

### 5.1 文档入库链路

```text
Markdown 文档导入
  -> Markdown 清洗
  -> 元数据提取
  -> 智能分块
  -> 全文索引写入 SQLite FTS5
  -> 向量索引写入 ChromaDB
  -> 入库完成
```

### 5.2 质检链路

```text
用户输入文本
  -> claim 拆分
  -> 实体提取
  -> Tier 1 规则校验
  -> 全文检索 + 向量检索
  -> 融合与重排
  -> 注入证据片段
  -> LLM 生成结构化质检结果
  -> 人工审核
  -> 审核结果持久化
```

### 5.3 上下文注入策略

MVP 不采用“整篇 Parent 文档默认全量注入”，改为分层注入：

1. 默认注入 `Top-N chunk + 邻接 chunk + 精确引用片段`
2. 若证据不足，再升级为 `章节级上下文`
3. 仅在争议问题中，手动触发 `整篇文档注入`

这样做的收益：

- 降低单次质检成本
- 缩短响应时间
- 减少长上下文噪声
- 提高结果可解释性

## 六、数据模型设计

### 6.1 文档主键设计

首版必须统一以下主键字段：

- `doc_id`：文献唯一标识
- `doc_title`：文献名称
- `edition`：版本，如第一版、修订版、内部版
- `source`：来源信息
- `section_id`：章节或条目 ID
- `page_no`：页码
- `span_id`：片段唯一标识
- `chunk_id`：分块 ID

### 6.2 Chunk 元数据最小结构

```json
{
  "chunk_id": "zhongguo_wenxue_001",
  "doc_id": "zhongguo_wenxue",
  "doc_title": "中国文学史纲要",
  "edition": "第一版",
  "section_id": "chapter_01_section_02",
  "page_no": 12,
  "chunk_type": "paragraph",
  "content": "先秦典籍中的语言风格具有明显的历史层次差异......",
  "keywords": ["先秦", "典籍", "语言风格"],
  "entities": ["先秦", "典籍", "语言风格"],
  "source_span": "第一章 第二节",
  "embedding_model": "text-embedding-v3"
}
```

### 6.3 实体归一最小要求

首版不做复杂知识图谱，但必须做最小实体归一：

- 标准名称
- 别名
- 繁简映射
- 常见异体字映射
- 领域术语分层维护

建议维护以下文件：

- `term_dictionary.json`
- `aliases.json`
- `variant_map.json`
- `domain_terms.json`

## 七、规则引擎设计

### 7.1 MVP 规则范围

首版只做高价值、可确定、低争议规则：

- 引用格式与出处完整性规则
- 标题层级与结构一致性规则
- 术语规范化规则
- 时间、数字、单位格式规则
- 可选医学规则包：剂量、禁忌、专业术语一致性

### 7.2 首版暂不做的规则

- 复杂领域推理规则
- 隐性语义型合规规则
- 高解释成本的组合推理规则
- 自动化跨文档因果判断

### 7.3 规则输出结构

规则命中后必须返回：

- `rule_id`
- `rule_name`
- `severity`
- `matched_entities`
- `reason`
- `source`
- `suggestion`

### 7.4 规则工程要求

- 规则数据与执行逻辑分离
- 规则文件支持版本号
- 规则结果必须可追溯
- 单位类规则必须先做单位归一
- 所有异常必须捕获并记录日志

## 八、质检输出结构

### 8.1 统一 verdict 枚举

- `verified`
- `contradicted`
- `suspected`
- `insufficient_evidence`
- `manual_review_required`

### 8.2 单条 claim 输出格式

```json
{
  "claim": "《论语》成书于春秋末期",
  "verdict": "verified",
  "confidence": 0.93,
  "reason": "知识库中存在明确原文支持",
  "evidence": "《论语》由孔子弟子及再传弟子编纂而成，约成书于春秋战国之际......",
  "source_doc": "中国哲学史",
  "source_span": "第一章",
  "retrieval_refs": ["chunk_101", "chunk_134"],
  "review_required": false
}
```

### 8.3 输出约束

- 没有证据时，不得输出 `verified`
- 证据与 claim 无法直接对应时，输出 `suspected` 或 `insufficient_evidence`
- `confidence < 0.70` 时默认标记 `manual_review_required`
- 高风险专业内容必须保留原始出处

## 九、评测方案

### 9.1 必须建立离线评测集

首版上线前至少准备以下数据集：

- 检索测试集：50 条问题与标准证据
- claim 测试集：50 条待核验陈述与人工标注结果
- 规则测试集：30 条规则命中样例与 30 条非命中样例
- 跨领域样例集：10 条古文或医学扩展样例

### 9.2 核心评测指标

| 维度 | 指标 | 目标 |
|------|------|------|
| 检索 | Top-5 命中率 | >= 80% |
| 检索 | Top-10 命中率 | >= 90% |
| 质检 | claim 判定准确率 | >= 80% |
| 质检 | 证据可追溯率 | >= 95% |
| 规则 | 误报率 | <= 5% |
| 规则 | 漏报率 | <= 5% |
| 性能 | 单次质检平均耗时 | <= 15 秒 |
| 成本 | 单次质检平均成本 | <= 0.20 元 |

### 9.3 评测执行方式

- 每次调整检索权重后，重新跑检索评测
- 每次调整 prompt 后，重新跑 claim 评测
- 每次调整规则数据后，重新跑规则回归测试
- 评测结果写入本地报表，作为是否升级到下一阶段的依据

## 十、异常处理与降级策略

### 10.1 文档导入降级

- Markdown 元数据抽取失败 -> 退化为最小元数据入库
- 标题层级识别失败 -> 退化为段落级分块
- 结构化字段缺失 -> 标记人工补录，不阻塞基础入库

### 10.2 检索降级

- 向量检索失败 -> 退化到 FTS5 全文检索
- 重排服务失败 -> 使用原始融合排序
- 实体识别失败 -> 保留原文关键词检索

### 10.3 LLM 降级

- 主模型超时 -> 切换备用模型
- 长上下文超限 -> 缩减为章节级注入
- 输出 JSON 解析失败 -> 触发一次结构化重试
- 连续失败 -> 转人工审核

### 10.4 成本降级

设置单次请求成本阈值和月度预算阈值：

- 超过单次阈值时，禁用章节级以上注入
- 超过月度阈值时，关闭争议场景的二次调用
- 超过预算上限时，仅保留规则校验和检索对照功能

## 十一、实施路径

### Phase 1：主链路跑通（1 至 2 周）

| 任务 | 交付物 |
|------|--------|
| Markdown 导入 | 可注册 Markdown 并完成基础入库 |
| 元数据抽取 | 文献、版本、页码、章节信息入库 |
| 分块与索引 | FTS5 + ChromaDB 可用 |
| 检索接口 | 关键词检索、语义检索、融合检索 |
| claim 质检 | 输出结构化 verdict |
| 审核记录 | SQLite 持久化 |

**阶段验收标准**：

- 导入 1 份 Markdown 后可检索到指定内容
- 输入 1 段文本可返回结构化 claim 结果
- 每条结果都能跳转到原始出处

### Phase 2：工程化增强（1 至 2 周）

| 任务 | 交付物 |
|------|--------|
| 规则引擎 | 通用规则 + 可选领域规则包 |
| 实体归一 | 别名、异体字、繁简映射、术语归一 |
| 审核台 | 问题高亮、证据展示、审核操作 |
| 缓存机制 | Embedding 与检索缓存 |
| 评测脚本 | 检索、claim、规则回归 |

**阶段验收标准**：

- 规则命中结果可解释、可追溯
- 检索和质检评测可重复执行
- 平均成本与平均耗时进入可控范围

### Phase 3：增强能力验证（按收益决定）

| 任务 | 说明 |
|------|------|
| 章节级长上下文注入 | 仅用于争议质检 |
| 结构化关系抽取 | 先做关系表，不急于图谱化 |
| 多版本比对 | 支持版本差异对照 |
| 图谱 PoC | 有明确收益后再做 |

## 十四、最终建议

本项目首版应坚持以下原则：

- 先做可验证的主链路，不提前投入复杂图谱能力
- 先保证证据可追溯，再追求复杂推理能力
- 先把规则、评测、审核闭环建立起来，再扩长上下文和多模型
- 先把“可用、可控、可维护”做扎实，再追求“最强能力上限”

如果后续评测结果表明特定领域检索明显受益于结构化关系建模，再引入 KG-RAG 会更稳妥。
