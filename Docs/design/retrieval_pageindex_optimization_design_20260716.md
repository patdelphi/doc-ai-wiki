# AI 检索与 PageIndex 优化设计

## 1. 文档状态

- 日期：2026-07-16
- 状态：已确认
- 已确认：总体架构、AI 检索流程、PageIndex 流程、测试、验收、回滚与执行边界
- 实施计划：`Docs/tasks/retrieval_pageindex_implementation_plan_20260716.md`
- 审计依据：`Docs/optimization-plan/retrieval_pageindex_audit_20260716.md`

## 2. 背景与目标

当前项目同时存在 SQLite FTS、Chroma 向量检索、AI 质检检索和 PageIndex 两套主流程。审计发现向量元数据与知识库过滤不一致、FTS 中文排序能力不足、混合检索缺少统一融合、PageIndex 索引扁平化、迭代焦点未驱动下一轮搜索、索引状态失真及评测集与真实知识库 ID 脱节等问题。

本次优化目标如下：

1. 建立清晰、可解释、可降级的统一检索管线。
2. 将 PageIndex 修正为真正的层级索引和预算受控的推理检索。
3. 使索引状态、模型指纹、数据数量和来源哈希可验证。
4. 用真实知识库评测证明优化有效，并支持安全回滚。
5. 所有修复、脚本、索引重建和结果报告均保存在项目内。

非目标：不进行无关 UI 重构，不引入长期双轨架构，不顺手清理与检索无关的模块，不执行部署或 Git 操作。

## 3. 实施策略

采用分阶段闭环修复，不一次性替换全部链路：

1. 安全基线：隔离测试环境，修复明确异常，增加索引诊断、备份、恢复和 SQLite WAL 配置。
2. AI 检索：完成中文词法召回、向量召回、RRF 融合、单次重排和统一轨迹，再重建一次检索索引。
3. PageIndex：完成层级树、文档路由、动态多轮检索和全局预算，再重建一次 PageIndex。
4. 评测收口：使用真实知识库评测，更新文档、变更记录、恢复说明和 CI 检查。

数据库迁移、外部模型调用和正式索引重建在执行前单独确认。

## 4. AI 检索设计

### 4.1 数据流

```text
查询规范化
→ 关键词召回 + 向量召回
→ RRF 融合与去重
→ 单次批量 Rerank
→ 阈值与无答案判断
→ 统一证据和检索轨迹
```

### 4.2 模块边界

- `RetrievalService`：只负责编排和降级控制。
- `lexical.py`：中文 FTS、BM25 和短词兜底。
- `fusion.py`：RRF、去重和排名轨迹。
- `vector_store.py`：向量召回及元数据校验。
- `index_state.py`：索引状态、模型指纹和一致性检查。
- `.aipython/rebuild_retrieval_indexes.py`：项目内备份、临时构建、验证、切换和恢复入口。

### 4.3 算法规则

1. 使用 FTS5 Trigram 和 BM25 改善中文词法召回与排序。
2. 两字短词使用受控兜底，不按更新时间充当相关性排序。
3. 词法和向量结果使用 RRF 融合，不直接比较两类原始分数。
4. 合并候选后最多执行一次批量 Rerank。
5. AI 质检只保留原文、规范化语义、边界或反例三类查询，统一召回后再排序。
6. 向量索引必须校验 `knowledge_base_id`、嵌入模型、向量维度、索引版本和文档数量。
7. 向量或 Rerank 失败时降级到本地检索，并返回 `degraded_reason`；不得静默标记为完整混合检索。
8. 索引不一致或缺少关键元数据时不得标记为 `indexed`。

### 4.4 检索索引重建

重建前备份 SQLite、Chroma 和索引清单，在临时位置构建新 FTS 与向量索引。只有数量、元数据、模型指纹、维度和聚焦评测全部通过后才原子切换。旧备份保留，不自动删除。

## 5. PageIndex 设计

### 5.1 索引结构

PageIndex 从扁平章节列表改为以下层级：

```text
文档
→ 篇章或卷
→ 章
→ 节
→ 可引用内容节点
```

每个节点保存稳定 `node_id`、`heading_path`、原文起止位置、来源锚点、内容摘要、`content_hash`、父子关系、索引版本和来源文件哈希。

### 5.2 单文档流程

```text
查询分析
→ 从根节点逐层选择候选
→ 加载叶子节点证据
→ 根据 next_search_focus 扩展下一轮
→ 证据判定
→ 生成带引用答案
```

### 5.3 知识库流程

```text
查询分析
→ 文档路由选择 Top 3 文档
→ 在全局预算内检索各文档树
→ 合并跨文档证据
→ 统一证据判定
→ 生成带引用答案
```

### 5.4 核心规则

1. `next_search_focus` 必须改变下一轮查询或候选节点，避免重复搜索。
2. 知识库查询先执行文档路由，不遍历全部文档。
3. 默认最多三轮节点扩展，并限制候选节点、证据数量和 LLM 调用总量。
4. PageIndex 的补充关键词和向量召回复用主 `RetrievalService`，删除重复 FTS/LIKE 逻辑。
5. 所有异常返回明确阶段、错误码和降级原因；修复未导入 `AppError` 等已确认异常路径。
6. 来源哈希不一致时标记 `stale_index`，禁止使用旧树生成确定性答案。
7. 证据轨迹统一记录文档、节点、标题路径、原文位置、选择轮次、选择原因和分数。

### 5.5 树质量门禁与重建

正式切换前必须检查正文覆盖率、层级深度、孤立节点、空节点、原文定位和随机回溯准确性。新 PageIndex 在临时目录生成，通过真实问题的节点命中和引用检查后原子切换，旧索引保留用于恢复。

## 6. 测试设计

### 6.1 测试隔离

测试启动时清除或覆盖真实 `.env` 中的管理员密码、模型地址和令牌，禁止单元测试隐式读取真实配置。外部 LLM、Embedding 和 Rerank 默认使用桩或假实现，真实服务验证单独执行并记录。

### 6.2 测试分层

1. 单元测试：Trigram/BM25、短词兜底、RRF、去重、阈值、降级、模型指纹和索引状态。
2. PageIndex 单元测试：标题层级、稳定节点 ID、原文锚点、文档路由、动态搜索焦点、预算和过期索引拒绝。
3. 集成测试：临时 SQLite、临时 Chroma、检索索引构建、PageIndex 构建、原子切换和恢复。
4. 回归测试：现有 API、AI 质检、单文档 PageIndex、知识库 PageIndex 和无答案保护。
5. 真实评测：使用当前项目真实文档 ID、知识库 ID 和人工标注证据，不继续使用失配的合成 ID 作为正式指标。

### 6.3 LLM 调用预算

- 单文档 PageIndex：查询分析 1 次、节点选择最多 3 次、证据判定 1 次、最终回答 1 次，合计最多 6 次。
- 知识库 PageIndex：在单文档预算基础上增加文档路由 1 次，合计最多 7 次。
- AI 质检：候选合并后最多执行一次批量 Rerank，不按每个查询变体重复重排。

## 7. 验收标准

### 7.1 正确性

- 真实评测集 Top-5 Recall 不低于 0.80。
- MRR@10 不低于 0.65，nDCG@10 不低于 0.70。
- PageIndex Node Hit@5 不低于 0.80。
- 无答案问题的拒答准确率不低于 0.90。
- 最终引用的原文可追溯率为 100%。
- SQLite 中应向量化的有效 chunk 数量与 Chroma 有效记录数量完全一致。
- Chroma 每条记录均包含正确的知识库、文档、模型和索引版本元数据。

### 7.2 性能与成本

- 本地检索 P95 延迟不高于优化前基线的 1.2 倍。
- AI 质检的重复检索和重排调用量相较当前流程至少下降 50%。
- PageIndex 不得超过既定 LLM 调用预算；超出时返回预算耗尽状态，不继续无限扩展。

### 7.3 工程质量

- 聚焦测试、全量测试、lint、type-check 和 build 全部通过。
- SQLite 连接统一启用 `PRAGMA journal_mode=WAL` 和 `PRAGMA synchronous=NORMAL`。
- 数据库修改使用事务，所有 API 路径具有明确异常处理。
- 索引诊断、重建、验证和恢复均有项目内脚本与文档。
- `Docs/optimization-plan`、`Docs/changelog`、`Docs/tasks` 及相关 API 文档与实际实现同步。

## 8. 回滚设计

1. 正式重建前生成带时间戳的数据库、Chroma、PageIndex 和索引清单备份。
2. SQLite 结构调整在事务内执行；新索引使用影子表或临时目录构建。
3. 新旧索引切换前执行数量、元数据、哈希、抽样检索和真实评测校验。
4. 任一门禁失败即停止切换，保留当前可用索引并生成失败报告。
5. 切换后验证失败时，通过项目内恢复脚本回到备份版本。
6. 备份不自动删除，删除操作必须再次取得确认。

## 9. 执行边界

执行顺序如下：

1. 先写失败测试并完成本地代码修复。
2. 运行不访问外部服务的聚焦测试和全量幂等校验。
3. 外部 LLM、Embedding、Rerank 真实验证前再次确认。
4. 数据库调整和正式索引重建前再次确认并说明备份与恢复方式。
5. 重建后生成项目内评测报告、变更记录和恢复记录。

未经确认不执行部署、数据库迁移、正式索引重建、依赖安装、Git commit、push、merge 或 pull。

## 10. 完成定义

只有在代码、索引、真实评测、异常降级、恢复演练和文档全部通过时，任务才视为完成。若指标未达标，必须保留旧索引，记录差距和阻塞原因，不以测试通过代替检索质量验收。
