# PageIndex 跨文档检索策略设计

> 时间：2026-06-23
> 范围：`src/pageindex/service.py`、`src/pageindex/question_plan.py`、`tests/unit/test_pageindex_service.py`、`tests/evaluation/pageindex_cases.jsonl`
> 目标：明确 PageIndex 在知识库多文档场景下如何筛选、读取、合并和回答，避免“每篇文档独立答一遍”或“只命中一个文档”的不稳定行为。

## 背景

当前 PageIndex 页面已经走知识库级入口，会遍历当前知识库下全部已构建 PageIndex 文档，并合并证据后回答。这个机制解决了“只搜单一文档”的问题，但还缺少更明确的跨文档检索策略：

- 哪些文档应该优先读？
- 多篇文档都相关时如何分配读取预算？
- 一篇文档证据充分时，是否还需要读其它文档？
- 多文档证据冲突或互补时，最终答案如何表达边界？

## 设计原则

- 搜索范围仍是当前知识库下所有已构建 PageIndex 的文档，不能跨知识库。
- 跨文档检索不替代单文档迭代检索，而是在单文档检索外增加“文档级规划与合并”。
- 优先保证证据覆盖和可解释性，再考虑性能优化。
- 默认最多读取少量高相关文档，避免每次问题都扫完整知识库。
- 若用户问题明显要求全库覆盖，例如“有哪些、汇总、比较、所有资料”，应扩大文档覆盖。

## 推荐流程

### 1. 文档级候选预筛

为每个 PageIndex 记录构建轻量文档画像：

- `doc_uid`
- 文档标题
- PageIndex 顶层节点标题
- 顶层摘要
- 已有 RAG/FTS 主题命中数量
- 最近一次构建状态

用用户问题、Question Plan 和文档画像生成文档候选排序。

### 2. 按问题类型分配读取预算

不同 `question_type` 使用不同策略：

| question_type | 文档覆盖策略 |
| --- | --- |
| `information_extraction` | 至少读取 top 2-3 篇相关文档，适合清单、方法、类别汇总 |
| `claim_judgement` | 先读最相关文档；若只有间接证据或风险提醒，再补读其它相关文档找反证或限定条件 |
| `source_location` | 优先返回最明确出处；除非用户要求全库出处，否则不扩大 |
| `comparison` | 尽量覆盖比较对象所在的不同文档 |
| `summary` | 读取覆盖面更广的文档和总论类节点 |
| `unknown` | 保守读取 top 1-2 篇，证据不足时明确说明 |

### 3. 单文档迭代检索

对进入预算的每篇文档调用现有单文档迭代检索：

1. 生成或复用检索阶段 Question Plan。
2. 构建候选节点。
3. LLM 选择节点并判断充分性。
4. 不足时继续下一轮。
5. PageIndex 主证据和同文档 RAG/FTS 补充证据合并。

### 4. 跨文档充分性判断

聚合证据后增加跨文档判断：

- 证据是否覆盖用户问题的主要对象。
- 是否有直接支持、反对、风险提醒、间接相关。
- 是否存在多文档冲突。
- 是否只来自单一文档，且问题本身要求全库汇总。

如果跨文档证据不足，可追加下一批文档预算；否则停止。

### 5. 最终回答

最终回答模板应显式知道：

- 命中了哪些文档。
- 每篇文档贡献了哪些证据。
- 哪些证据直接回答问题，哪些只是背景或限定。
- 若只覆盖部分文档，必须说明“基于当前命中文档”。

## 分阶段实施

### P0：只做可观察性

- 在知识库级 PageIndex debug 中增加 `document_candidates`。
- 记录每篇文档是否进入检索、是否有证据、证据数量。
- 不改变现有检索结果。

### P1：文档预算策略

- 根据 Question Plan 设置默认 `max_documents`。
- `information_extraction` 和 `comparison` 默认读取更多文档。
- `source_location` 和明确单点问题默认读取更少文档。

### P2：跨文档充分性判断

- 聚合后判断是否需要追加文档检索。
- 证据不足或冲突时，最多追加一批文档。
- 在最终回答中说明覆盖范围和不足。

## 验收标准

- 知识库级 PageIndex debug 能看到文档候选、文档预算和每篇文档贡献。
- “阿胶有哪些质量检测方法”这类信息抽取问题，不会因为第一篇文档有部分证据就停止。
- “某一句话出处在哪”这类定位问题，不会无意义读取全部文档。
- 多文档证据冲突时，最终答案能明确说明冲突来源。
- 单测不调用外部 API。

## 暂不做

- 不引入新的向量库或外部 PageIndex 服务。
- 不改变现有 `pageindex_indexes` 表结构。
- 不把所有文档全文塞进同一个 LLM prompt。
- 不在没有 debug 可观察性前直接改文档预算策略。
