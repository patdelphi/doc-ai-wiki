# AI 检索与 PageIndex 优化前后对比

## 1. 总体结论

本轮优化不是单点调参，而是把原项目中相互分散、存在隐式降级和索引不一致的两套检索流程，收敛为职责清晰、可追溯、可验证、可备份恢复的工程链路。

已确认的提升包括：中文词法召回、混合排序、向量索引完整性、单次重排、证据追溯、PageIndex 层级结构、调用预算、索引发布安全和自动化检查。正式 Recall、MRR、nDCG 与 PageIndex Node Hit 指标仍需独立人工重标后才能判断，不能用旧索引自动候选冒充金标。

## 2. 核心流程对比

| 维度 | 原项目 | 当前版本 | 实际提升 |
|---|---|---|---|
| 中文全文检索 | 旧 FTS 使用 `unicode61`，长中文查询容易整体匹配失败 | 使用 Trigram FTS；三字及以上走 BM25，两字词走受控 LIKE 兜底 | 中文连续文本和短词召回更稳定 |
| 查询归一 | 别名、繁体、标准名处理分散 | 统一实体词表与 query normalization | `阿膠`、`驴皮胶` 等问法可归一到阿胶语义 |
| 混合排序 | 词法分数与向量分数职责不清，异构分数难直接比较 | 词法与向量排名统一使用 RRF：`sum(1 / (60 + rank))` | 排序口径明确，不依赖不同模型原始分数量纲 |
| 查询变体 | AI 质检可能生成多种查询并反复执行重排 | 最多保留原文、语义归一、反证探测三类查询；合并候选后只 Rerank 一次 | 降低重复调用和候选互相覆盖 |
| Rerank 降级 | HTTP 失败时可能原样返回，调用方无法判断是否真实重排 | 评测统计 `rerank_score`、Rerank 覆盖率和降级样例数；Smoke Test 拒绝静默假成功 | 外部服务是否真实生效变得可观测 |
| 向量知识库隔离 | 部分向量缺少 `knowledge_base_id` | 全量向量继承文档知识库 ID，查询支持知识库过滤 | 避免跨知识库混检 |
| 向量结果元数据 | 主要依赖 Chroma 中可能滞后的 metadata | 返回前以 SQLite 事实源刷新文档和 chunk 追溯字段 | 向量结果可稳定回到原文位置 |
| PageIndex 补充检索 | PageIndex 内存在独立检索逻辑，容易与主检索漂移 | PageIndex 统一调用 `RetrievalService.hybrid_search()` | 两套流程共享同一召回、隔离和追溯规则 |

## 3. 真实索引状态提升

### 优化前

- SQLite chunk：4207。
- Chroma vector：2145。
- 缺少必要向量 metadata：2145。
- `阿胶历史文化通典` 向量数：0。
- 向量模型、维度和索引版本指纹不完整。
- FTS tokenizer：`unicode61`。

### 优化后

- SQLite chunk：4207。
- Trigram FTS chunk：4207。
- Chroma vector：4207。
- 默认知识库向量：4206；验收知识库向量：1。
- 缺失必要向量 metadata：0。
- Embedding：Qwen3-Embedding-8B，1024 维。
- 索引版本：`retrieval-v2`。
- 最终一致性：`consistent=true`。

## 4. 证据追溯提升

### 优化前

- 4207 个 chunk 中，`heading_path`、`source_start_line` 和 `source_anchor` 均为空。
- 检索虽然能返回内容，但无法稳定定位到标题路径和原文行号。
- 评测证据追溯率为 0。

### 优化后

- 通过稳定 `section-n` 映射，事务化回填 1164 个章节和 4206 个业务 chunk。
- 保持原 doc、section、chunk ID 和 chunk 内容不变。
- 业务 chunk 具备标题路径、起止行号、source anchor 和 chunk 类型。
- 50 条真实混合检索评测证据追溯率为 1.0。
- 独立验收知识库的 1 个示例 chunk 未混入默认知识库评测。

## 5. PageIndex 算法与工程提升

| 维度 | 原项目 | 当前版本 |
|---|---|---|
| Markdown 建树 | vendor 对大量节点并发调用 LLM，真实重建触发并发配额超限 | Markdown 使用确定性本地标题树，不依赖 LLM 建树 |
| 层级结构 | 源转换结果大量标题为 H1，容易形成扁平树 | 恢复卷、章、数字编号、中文序号和常见章节层级 |
| 节点标识 | 依赖 vendor 输出 | 使用文档、标题路径和原文范围生成稳定节点 ID |
| 质量门禁 | 结构是否可用缺少统一发布门槛 | 校验根节点、最大深度、空节点、孤立节点、重复 ID、追溯率和源覆盖率 |
| 陈旧索引 | 源文件变化后可能继续读取旧结构 | 数据库与 workspace 保存 source hash，不一致时标记 stale |
| 查询词提取 | `抗贫血研究` 等长短语可能无法命中 `抗贫血` 标题 | 去除“研究、资料、信息、情况”等泛化尾词，同时保留原长词 |
| 调用控制 | 调用次数与重试边界不清晰 | 单文档、知识库级检索都有最大 LLM、轮数、文档数和证据数预算 |
| PDF 兼容 | vendor PageIndex 流程 | 保留 vendor + LLM 流程，并补齐 Base URL 环境桥接 |

真实重建结果：

- `阿胶历史文化通典`：352 个节点，1 个根节点，最大深度 4。
- `阿胶学术论文全集`：953 个节点，1 个根节点，最大深度 6。
- 两份文档追溯率、源覆盖率均为 1.0，无空节点、孤立节点和重复节点 ID。
- Markdown PageIndex 两份文档最终重建约 9 秒，避免数百次节点级 LLM 调用。

## 6. 安全性与可恢复性提升

### 原项目风险

- 向量维度冲突可能在启动阶段触发无备份修复。
- 索引重建缺少统一的 staging、校验和原子切换流程。
- Windows 下 Chroma 句柄未显式关闭，失败清理可能出现 `WinError 5`。
- 重建失败异常可能被后续清理异常覆盖。

### 当前版本

- 启动阶段不再无备份删除或重建向量索引。
- 检索和 PageIndex 都提供 `inspect / rebuild / restore` 命令。
- 正式重建采用备份、staging 构建、质量校验、原子发布和 previous 保留。
- Chroma 客户端显式 `close()`，避免 Windows 文件锁。
- 清理失败单独记录，不覆盖原始构建或校验错误。
- 检索、PageIndex 和追溯字段均有可用备份；恢复命令已完成 dry-run。

## 7. 可观测性与验证提升

- 模型连通性检查分别验证 LLM、Embedding、Rerank，并拒绝 Rerank 静默回退假绿。
- 索引状态报告同时输出 SQLite、FTS、向量数量、知识库分布、文档分布、模型、维度、版本和一致性错误。
- 评测报告新增 Recall@5、MRR@10、nDCG@10、证据追溯率、Rerank 覆盖率和降级样例数。
- CI 与 PR 模板统一要求 Ruff、Pytest、Mypy 和 build。
- 最终验证：Ruff 通过；Pytest `390 passed, 6 warnings`；Mypy 18 个目标文件通过；build 和 compileall 通过。

## 8. 当前不能宣称的提升

以下指标尚不能专业地声称“已经提升”：

1. Recall@5、MRR@10、nDCG@10：当前 50 条标签来自旧索引自动候选首条结果，不是独立人工金标。
2. PageIndex Node Hit@5、拒答准确率：现有 55 条样例引用虚构文档 ID 和旧节点标题。
3. 生产环境吞吐与延迟：尚未部署，也未执行持续并发压测。
4. 所有 PageIndex LLM 问答质量：真实 LLM 连通性已验证，但未用重新标注的 55 条问题做完整端到端评分。

因此，当前可以确认的是：架构、索引完整性、中文召回基础、证据追溯、PageIndex 结构、调用可观测性、重建安全和工程质量均有实质提升；最终相关性质量需要人工金标完成后再下结论。
