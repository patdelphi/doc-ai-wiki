# 专业知识库技术与用户需求成熟度评估

> 评估日期：2026-07-16
>
> 评估对象：`codex/retrieval-pageindex-optimization` 分支
>
> 评估范围：知识入库、AI 检索、PageIndex、证据追溯、AI 质检、人工审核、权限、可恢复性、评测与用户体验

## 1. 总体判断

当前项目已经明显超过“向量库 + 聊天框”的普通 RAG 原型，具备中文专业知识库的完整业务骨架，定位应为：

- 面向本地或私有化部署：成熟试点级，接近准生产级。
- 面向中小规模、低并发、专业资料治理：具备实际使用价值。
- 面向企业级高并发、强合规和可量化 SLA：尚未达到正式生产级。

综合成熟度建议评为 `6.8/10`。如果只评价当前约 4207 个 chunk 的本地专业知识库场景，可评为 `7.5/10`；如果按企业级生产系统标准评价，约为 `6.0/10`。

核心原因不是算法路线落后，而是“工程能力已经比较完整，质量证据和线上运营闭环仍不足”。

## 3. 已达到专业水准的部分

### 3.1 知识库不是单一问答功能，而是完整业务闭环

项目已经串联：

`文档入库 -> 索引构建 -> 混合检索 -> AI 质检 -> 人工审核 -> 结果导出`

同时具备多用户、多知识库权限和历史记录。这比只关注回答生成的 RAG 项目更接近真实知识管理产品。

### 3.2 检索算法路线正确

当前主检索流程为：

`查询归一 -> 中文词法召回 + 向量召回 -> RRF 融合 -> Rerank -> 上下文扩展 -> 证据输出`

优点包括：

- 中文连续文本使用 FTS5 Trigram/BM25，两字短词采用受控 LIKE 补充。
- 向量召回负责语义泛化，词法召回保留专业名词、数字和原文精确匹配能力。
- 使用 RRF 处理词法分数和向量分数量纲不一致问题。
- 多查询候选合并后只执行一次 Rerank，避免重复调用和排序互相覆盖。
- Embedding 或 Rerank 失败会显式标记降级，不再静默假成功。

这与当前主流混合检索实践一致。Elastic 和 Azure AI Search 的官方方案同样采用全文与向量并行召回，再使用 RRF 统一排序。

### 3.3 两套检索流程的职责已经比较清楚

- AI 检索适合跨文档、事实型、关键词型和语义型查询。
- PageIndex 适合长文档、目录层级清晰、需要沿章节结构推理的问题。
- PageIndex 的补充证据统一调用主 `RetrievalService`，减少两套算法长期漂移。

当前 PageIndex 已具备本地确定性 Markdown 建树、稳定节点 ID、文档路由、树候选选择、迭代检索、证据充足性判断和调用预算，符合 PageIndex 官方强调的“层级结构 + 推理式检索”方向。

### 3.4 可信证据链是项目的明显优势

当前 4207 个 chunk、FTS 和向量数量一致，业务 chunk 已回填标题路径、原文行号、来源锚点和内容 hash。50 条真实检索运行的证据追溯率为 1.0。

对于医学、古籍、企业制度和内容合规等专业场景，能够回答“依据是什么、来自哪里、能否回到原文”比只生成流畅答案更重要。

### 3.5 索引工程和恢复能力已经超过一般原型

检索索引和 PageIndex 都具备：

- inspect；
- backup；
- staging rebuild；
- 质量校验；
- 原子发布；
- previous 保留；
- restore dry-run。

真实索引已达到 SQLite、Trigram FTS 和 Chroma 各 4207 条且 `consistent=true`。这部分已经具有较好的生产意识。

### 3.6 测试和权限底座较扎实

- 当前收集到 390 项测试，最近一次完整验证为 390 项通过。
- 接口测试覆盖未授权知识库访问、检索、质检、审核、重建等关键权限边界。
- CI 和 PR 模板已要求 Ruff、Pytest、Mypy 和 build。

## 4. 当前最关键的不足

### 4.1 尚不能证明检索质量已经优秀

现有 50 条检索标签来自旧索引自动候选，不是独立人工金标；55 条 PageIndex 样例仍引用虚构文档 ID 和旧节点标题。因此：

- Recall@5 `0.14`、MRR@10 `0.1002`、nDCG@10 `0.1144` 不能证明新算法差；
- 也不能用索引一致、Rerank 覆盖率 1.0 来证明相关性优秀；
- 当前只能确认“流程真实运行、索引完整、证据可追溯”，不能确认“用户总能拿到最相关答案”。

这是从成熟试点迈向专业生产系统的第一阻断项。

### 4.2 缺少线上效果闭环

代码中已有 `request_id`，但未发现系统化的检索事件日志和质量运营指标，例如：

- 各阶段 p50/p95 延迟；
- 查询类型、召回通道、候选数量、Rerank 和 LLM 调用次数；
- 零结果率、拒答率、降级率、引用点击率；
- 用户“有帮助/无帮助”、纠错、人工选中证据；
- 模型、Prompt、索引版本与答案结果的关联。

没有这些数据，后续优化仍会依赖工程人员主观抽样，难以持续证明用户价值。

### 4.3 PageIndex 的真实规模验证不足

当前真实 PageIndex 只有 2 个文档、352/953 个节点。结构质量已验证，但尚未验证：

- 数十到数百份长文档下的文档级路由准确率；
- 跨文档问题的召回、合并和引用正确性；
- 大目录、多跳引用和表格密集文档的效果；
- Node Hit@5、拒答准确率、答案忠实度和成本曲线。

### 4.4 终端用户操作仍偏工程化

- 入库主要围绕 `Input/<knowledge_base_id>` 目录扫描，未发现面向普通用户的直接上传入口。
- 搜索只支持知识库和文档范围，尚未把作者、来源、标签、时间等已有元数据变成筛选条件。
- 未发现搜索结果和 PageIndex 答案的用户反馈、纠错和证据确认入口。
- 降级原因对工程排障有价值，但需要转换为用户能理解的状态说明。

### 4.5 核心模块过大

当前文件规模：

- `src/ui/pages.py`：6749 行；
- `src/pageindex/service.py`：2716 行；
- `src/quality/service.py`：1293 行。

测试能够降低回归风险，但文件仍同时承担编排、算法、持久化、格式化和兼容逻辑。继续增加算法分支后，可读性和定位效率会明显下降。

### 4.6 安全治理仍需补齐

项目已有知识库权限隔离，这是优点；但未发现完整的：

- 非可信文档 Prompt Injection 检测与隔离；
- 文档指令和系统指令的明确边界；
- 查询审计、敏感信息脱敏和日志保留策略；
- 用户/API 速率限制、模型调用配额和成本限额；
- 高风险结论的强制引用和人工确认策略。

## 5. 下一步升级路线

### P0：先建立可信质量基线

1. 建立人工金标集：至少 200 条检索问题、100 条 PageIndex 问题。
2. 按精确事实、别名、长问题、跨章节、跨文档、反证、无答案、权限隔离等类型分层。
3. 每条记录相关 chunk/node、答案要点、应拒答标记和风险等级。
4. 双人标注并处理分歧，保留标注依据。
5. 固定模型、Prompt、索引和评测集版本，输出可比较的基线报告。

建议初始验收门槛：

| 指标 | 建议门槛 |
|---|---:|
| Recall@5 | >= 0.85 |
| MRR@10 | >= 0.70 |
| nDCG@10 | >= 0.75 |
| PageIndex Node Hit@5 | >= 0.85 |
| 无答案/拒答准确率 | >= 0.90 |
| 引用定位正确率 | >= 0.95 |
| 证据追溯率 | 1.00 |
| 无证据却输出确定结论 | 0 |

这些门槛是首版建议，应根据医学、合规等场景风险再提高。

### P0：增加线上可观测性和反馈闭环

新增统一 `retrieval_event`，记录：

- request/query/user/knowledge-base ID；
- 查询规范化结果和路由模式；
- 各召回通道候选、排名和耗时；
- Rerank、LLM、PageIndex 调用次数、模型和版本；
- 降级原因、最终证据、拒答状态和总耗时；
- 用户反馈、纠错和人工确认结果。

需要同时规定敏感数据脱敏、日志访问权限和保留周期。

### P1：提升真实用户体验

1. 增加拖拽上传、批量入库、任务进度、失败重试和重复文档提示。
2. 增加作者、来源、标签、时间、文档类型等结构化筛选。
3. 搜索结果提供“为什么命中”、原文定位、相邻上下文和引用复制。
4. PageIndex 答案提供证据树路径、引用展开、回答模式和不确定性说明。
5. 增加有帮助/无帮助、问题原因和正确证据选择，直接沉淀训练/评测样本。

### P1：升级 PageIndex 文档级路由

在当前节点树之前增加知识库级文档目录树或文档摘要索引：

`问题计划 -> 文档级路由 -> 文档内树检索 -> 混合检索补充 -> 证据充足性 -> 回答/拒答`

重点评测多文档路由召回率、跨文档合并、调用预算和延迟，避免知识库文档增多后让 LLM 直接遍历所有文档。

### P1：拆分核心服务

保持现有外部接口不变，按职责做最小拆分：

- PageIndex：索引、路由、树检索、证据、回答、历史/导出；
- AI 质检：查询计划、候选召回、证据判断、结论编排、持久化；
- UI：页面装配、事件处理、视图格式化。

先补边界测试，再逐模块迁移，不进行一次性大重写。

### P2：性能、容量与安全门禁

1. 建立 1 万、10 万、100 万 chunk 的容量和并发测试曲线。
2. 分别记录普通检索与 PageIndex 问答的 p50/p95、吞吐、模型成本和降级率。
3. 根据测试结果决定是否继续使用 SQLite/Chroma；当前规模不需要为了“看起来先进”提前迁移。
4. 增加文档 Prompt Injection、越权引用、敏感信息和恶意文件回归集。
5. 加入速率限制、用户配额、API 审计和高风险回答人工确认。
6. 有足够点击和人工反馈数据后，再评估 Learning-to-Rank；当前阶段不应提前引入。

## 6. 建议执行顺序

1. 人工金标与正式评测；
2. 检索事件日志和用户反馈；
3. 基于真实错误类型调整召回、RRF、Rerank 和拒答阈值；
4. 文档上传、元数据筛选和证据交互；
5. PageIndex 多文档路由与规模验证；
6. 核心模块拆分；
7. 压测、安全测试与生产门禁。

不建议下一步直接更换向量库、增加更多模型或继续堆叠复杂 Agent。当前最有价值的升级，是让每次算法调整都能被人工金标、真实用户反馈和线上指标证明。

## 7. 最终结论

本项目的优势是“专业知识治理流程完整、证据意识强、双检索架构合理、索引工程可靠”；短板是“质量尚未被可靠数据证明、线上用户闭环不足、规模和运维能力未验证”。

下一阶段应从“继续建设功能”切换到“质量运营与生产验证”。完成 P0 后，项目可以从成熟试点提升为有客观证据支撑的准生产系统；完成 P1 和 P2 后，才适合按企业级专业知识库对外承诺 SLA。

## 8. P0 工程修复执行结果

本轮已把评估中影响正确性和门禁可信度的三项问题落地修复：Rerank 失败显式降级、授权多知识库一次全局排序、两个检索核心模块恢复 Mypy 检查。最新本地验证为 Ruff 通过、Mypy 19 个目标文件通过、完整测试 `402 passed, 6 warnings`、构建与 compileall 通过。

该结果提升了权限范围内排序正确性和 CI 可信度，但不改变人工金标、线上可观测性、用户反馈、PageIndex 多文档规模和生产 SLA 尚未完成的判断。因此成熟度总分暂不因工程测试通过而上调，待 P1/P2 产生真实质量与用户数据后再复评。

P1 第一批已清理 UI/认证相关 185 个 F401/F841 问题、重复权限 helper 和历史重导出，并恢复对应 Ruff 门禁。此项降低了继续拆分 UI 的噪声和回归风险，但 `build_ui()` 与 PageIndex 巨型服务仍未完成职责拆分，因此可维护性短板只算部分改善。

该批次最终验证为 Ruff、Mypy、build、compileall 通过，完整测试 `404 passed, 6 warnings`。
