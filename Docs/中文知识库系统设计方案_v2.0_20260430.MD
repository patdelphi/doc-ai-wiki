# 医学古籍知识库与 AI 质检系统

> **版本**：v2.0  
> **日期**：2026-04-30  
> **状态**：设计方案

---

## 一、核心功能模块

| 模块 | 功能 | 关键指标 |
|------|------|----------|
| **文档处理引擎** | PDF → MD，医学古文精准识别 | 文字版 PDF，复杂排版，保留方剂/表格结构 |
| **知识库引擎** | 文档向量化 + 知识图谱 + 全文检索 | KG-RAG 增强检索 + 百万 token 全量注入 |
| **AI 质检引擎** | 手动输入 → 规则校验 → 知识库交叉验证 → 疑点标注 | ≤2000字/次，claim-by-claim 验证，确定性守卫 |
| **运营管理** | 文档上传、知识库维护、质检记录 | 版本管理、原文溯源、审核历史 |

- 编排层用 LlamaIndex，RAG 抽象成熟，原生支持 PropertyGraph

## 三、模块详细设计

### 3.1 PDF → Markdown 解析 Pipeline

**确认前提**：PDF 是**文字版**（非扫描件），但包含复杂排版和医学古文。

```
PDF 上传
  ↓
┌─────────────────────────────────────────────────────┐
│ 步骤 1：Docling 解析（主力引擎）                       │
│                                                     │
│ · 提取文字内容（保留原始编码）                         │
│ · 识别表格结构（方剂组成、药材剂量表）                  │
│ · 识别标题层级（卷、篇、章、条）                        │
│ · 识别注释/脚注/夹注                                 │
│ · 输出初始 Markdown                                  │
│                                                     │
│ 中文支持：Docling 原生 Unicode，OCR 用 RapidOCR       │
│ 速度：~0.05秒/页，几十份 PDF 分钟级完成                 │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ 步骤 2：LLM 精校（云端 API）                           │
│                                                     │
│ 模型：Qwen-Max 或 Qwen3（中文古文能力强）              │
│ 任务：                                                │
│ · 古文断句/标点补全                                    │
│ · 医学专有名词校对                                    │
│ · 异体字/繁体 → 统一简体（或保留+标注）                │
│ · 排版歧义消解（多栏阅读顺序）                         │
│ · 表格内容对齐校验                                    │
│                                                     │
│ 成本：几十份 PDF，一次性约 ¥5-20                      │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ 步骤 3：知识图谱实体抽取（LLM 直接抽取）                │
│                                                     │
│ 利用 LLM 的强大 NER 能力，直接从解析后的 Markdown      │
│ 中抽取医学实体及关系，构建知识图谱三元组：              │
│                                                     │
│ · 方剂 → 包含 → 药材                                 │
│ · 方剂 → 主治 → 病证                                 │
│ · 药材 → 性味 → 性/味/归经                           │
│ · 药材 → 反畏 → 药材（十八反/十九畏）                 │
│ · 药材 → 功效 → 功效描述                              │
│ · 病证 → 治法 → 治法                                 │
│                                                     │
│ 输出：三元组 → 存入 LlamaIndex PropertyGraph           │
│ 优势：无需本地 NER 模型，LLM 直接抽取，准确率高        │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ 步骤 4：输出                                          │
│ · Markdown 文件 → ./data/docs/                       │
│ · 知识图谱三元组 → PropertyGraph                     │
│ · 元数据 JSON（来源、版本、页数、置信度）               │
└─────────────────────────────────────────────────────┘
```

**引擎选型依据**：

| 引擎 | 适用场景 | 优先级 |
|------|---------|--------|
| **Docling** | 文字版 PDF，复杂排版，表格 | **主力** ✅ |
| **MinerU** | 扫描件 PDF，中文优化好 | 备用（扫描件场景） |
| **LLM 端到端** | 极端复杂排版兜底 | 兜底 |

### 3.2 知识库引擎（KG-RAG 增强）

#### 3.2.1 三层知识表示

```
知识层级
│
├── 第一层：文档层（原始 Markdown）
│     · PDF 解析后的完整 Markdown 文档
│     · 保留原始结构、表格、注释
│     · 用于长窗口全量注入（50K-500K tokens）
│
├── 第二层：向量层（语义检索）
│     · 按医学语义边界智能分块（非固定字数）
│     · 每个 chunk 200-2K tokens
│     · Embedding → ChromaDB 向量索引
│     · 用于语义相似性召回
│
├── 第三层：图谱层（知识图谱）
│     · 实体-关系三元组（方剂-药材-病证等）
│     · LlamaIndex PropertyGraph 存储
│     · 用于精确关系查询、多跳推理
│     · 示例：桂枝汤 → 包含 → 桂枝 → 性味 → 辛温
│
└── 第四层：全文层（精确匹配）
      · SQLite FTS5 全文索引
      · 用于术语精确匹配、古文原文检索
```

**Chunk 元数据结构**：

```json
{
  "chunk_id": "shanghan_vol3_item5",
  "doc_name": "伤寒论",
  "doc_version": "宋本",
  "chunk_type": "方剂",
  "content": "桂枝汤方：桂枝三两（去皮），芍药三两，甘草二两（炙）...",
  "summary": "桂枝汤的组成、剂量与煎服法",
  "entities": {
    "方剂": ["桂枝汤"],
    "药材": ["桂枝", "芍药", "甘草", "生姜", "大枣"],
    "剂量": ["三两", "二两", "十二枚"],
    "病证": ["太阳病", "中风"]
  },
  "keywords": ["桂枝汤", "解肌发表", "调和营卫"],
  "parent_id": "shanghan_vol3",
  "position": {"page": 45},
  "embedding_model": "通义text-embedding-v3"
}
```

#### 3.2.2 知识图谱设计

**医学古籍核心三元组**：

```
┌──────────┐    包含     ┌──────────┐    性味     ┌──────────┐
│  方剂     │────────────▶│  药材     │────────────▶│  性/味    │
│ 桂枝汤    │            │  桂枝     │            │ 辛/温    │
│ 麻黄汤    │            │  麻黄     │            │ 辛/微苦/温│
│ 小柴胡汤  │            │  柴胡     │            │ 苦/微寒   │
└──────────┘            └──────────┘            └──────────┘
     │                       │                       │
   主治                    反畏                   归经
     │                       │                       │
     ▼                       ▼                       ▼
┌──────────┐    配伍     ┌──────────┐    所属     ┌──────────┐
│  病证     │◀────────────│  药材     │────────────▶│  经络     │
│ 太阳病    │            │  甘草     │            │ 脾经      │
│ 少阳病    │            │  藜芦     │            │ 肺经      │
└──────────┘            └──────────┘            └──────────┘
```

**图谱存储方案**：

| 方案 | 说明 | 选型 |
|------|------|------|
| **SimplePropertyGraphStore** | LlamaIndex 内置，内存/JSON 存储，零运维 | **MVP 首选** ✅ |
| Neo4j Community | 独立图数据库，适合大规模 | Phase 3 按需迁移 |

为什么选内存图谱：
- 几十份古籍文档，三元组总量不超过几万条
- 无需 Docker，无需额外端口
- LlamaIndex 原生支持，一行代码切换
- 重启后 JSON 持久化，加载即用

#### 3.2.3 KG-RAG 增强检索

```
用户查询 / 质检文本
  ↓
┌─────────────────────────────────────────────────────┐
│ 智能路由（意图识别 → 云端轻量 LLM）                    │
│                                                     │
│ 判断查询类型：                                       │
│ · 语义问答 → 走向量检索路径                          │
│ · 关系查询 → 走图谱检索路径                          │
│ · 精确术语 → 走全文检索路径                          │
│ · 复合查询 → 三路并行                                │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ 第一层：多路召回（并行）                               │
│                                                     │
│ ┌──────────────┐  ┌──────────────┐  ┌────────────┐  │
│ │ 向量检索      │  │ 图谱检索      │  │ 全文检索    │  │
│ │              │  │              │  │            │  │
│ │ 通义 Embedding│  │ PropertyGraph│  │ SQLite     │  │
│ │ + ChromaDB   │  │ 子图遍历      │  │ FTS5       │  │
│ │ Top-30       │  │ Top-20 实体  │  │ Top-20     │  │
│ └──────────────┘  └──────────────┘  └────────────┘  │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ 第二层：融合去重（RRF 加权合并）                       │
│ · 三路结果合并去重                                   │
│ · 加权融合（向量 0.4 + 图谱 0.4 + 全文 0.2）          │
│ · 候选集：Top-50                                     │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ 第三层：云端重排（Cross-Encoder API）                  │
│                                                     │
│ 方案 A：通义 rerank API（阿里云 DashScope）            │
│ 方案 B：Cohere Rerank API（海外）                     │
│                                                     │
│ · 对 50 个候选逐一打分                               │
│ · 按相关性排序，取 Top-15                            │
│ · 成本：每次 ¥0.01-0.03                              │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ 第四层：长窗口全量注入                                 │
│                                                     │
│ · 将 Top-15 相关 chunk 的完整 Parent 文档注入 LLM    │
│ · 可能达到 50K-500K tokens                           │
│ · LLM 在完整上下文中做深度理解                        │
│                                                     │
│ 模型路由：                                           │
│ · ≤200K tokens → Claude Sonnet 4                    │
│ · 200K-1M tokens → Gemini 2.5 Pro                   │
│ · 中文古文专项 → Qwen3-235B                         │
└─────────────────────────────────────────────────────┘
```

**为什么做 KG-RAG 而不是纯向量 RAG**：
- 2026年顶会论文验证：KG-RAG 比纯向量 RAG 在复杂问答上提升 **10-18%**
- 医学古籍天然适合 KG——"方剂→药材→功效→病证"是典型的三元组网络
- 图谱检索解决向量检索的致命弱点：精确关系查询、多跳推理、可解释溯源
- 示例："桂枝汤中哪些药材与藜芦相畏？" → 图谱一步到位，向量检索做不到

#### 3.2.4 Embedding 与 Reranker 选型（云端）

| 组件 | 选型 | API 提供方 | 费用 |
|------|------|-----------|------|
| **Embedding** | 通义 text-embedding-v3 | 阿里云 DashScope | ¥0.7/百万 tokens |
| **Reranker** | 通义 rerank 或 Cohere rerank | 阿里云 / Cohere | ¥10/百万 tokens |

替代方案：
- Embedding 也可用 OpenAI text-embedding-3-large（$0.13/百万 tokens）
- Reranker 也可用 Jina Reranker（开源但需本地，暂不考虑）

### 3.3 AI 质检引擎（核心亮点）

#### 3.3.1 三层质检架构

```
用户输入（≤2000字文本，选择质检场景模板）
  ↓
┌─────────────────────────────────────────────────────┐
│ Tier 1：确定性规则校验（Python 轻量规则，免费）         │
│                                                     │
│ 将中医领域中"不容出错"的硬规则从 LLM 判断中剥离，     │
│ 用确定性规则引擎先行校验，确保不犯低级错误：           │
│                                                     │
│ · 配伍禁忌规则（如十八反、十九畏等）                   │
│ · 剂量限制规则（药典推荐量、古籍极量等）               │
│ · 禁忌症规则（孕妇禁忌、毒性药材等）                   │
│ · 法规合规规则（药典收录、处方权限等）                 │
│ · 其他领域硬规则（按需扩展）                           │
│                                                     │
│ 输出：触发规则 → 直接标记"contradicted"，不送 LLM    │
│ 优势：100% 确定性，零成本，零幻觉                     │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ Tier 2：文本分析与知识库检索（云端 LLM + KG-RAG）     │
│                                                     │
│ 步骤 1：文本分析（Qwen-Max，成本低）                  │
│ · 分句，提取独立论断（claim）                         │
│ · 提取医学实体（药材/方剂/穴位/病证）                  │
│ · 分类：事实陈述 / 观点 / 引用 / 数据                  │
│                                                     │
│ 步骤 2：KG-RAG 知识库检索                            │
│ · 向量 + 图谱 + 全文三路召回                         │
│ · 云端重排精筛                                       │
│ · 取 Top-15，注入完整 Parent 文档                     │
│                                                     │
│ 步骤 3：深度分析（Claude Sonnet 4 / Gemini 2.5）     │
│ · 逐条 claim 对比知识库                              │
│ · 输出结构化 verdict + confidence + evidence         │
│                                                     │
│ 示例输出：                                           │
│ [                                                    │
│   {"claim": "黄芪能补气升阳",                         │
│    "verdict": "verified",                            │
│    "confidence": 0.95,                               │
│    "evidence": "《神农本草经》：黄芪，味甘微温...",    │
│    "source_doc": "本草纲目·卷二十一"},                │
│   {"claim": "黄芪每日可用至120g",                     │
│    "verdict": "suspected",                           │
│    "confidence": 0.65,                               │
│    "reason": "古籍最大剂量未见超60g",                  │
│    "evidence": "《中国药典》2020版：9-30g",           │
│    "suggestion": "建议核实是否为特殊用法"},            │
│ ]                                                    │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ Tier 3：争议内容多模型投票（仅 confidence < 0.7）      │
│                                                     │
│ 对低置信度 claim：                                    │
│ · 用第二个模型（Qwen3-235B）独立判断                  │
│ · 两个模型一致 → 提高置信度                           │
│ · 两个模型不一致 → 标记"争议"，交人工判断              │
│                                                     │
│ 成本：仅对争议内容调用，单次增加 ¥0.05-0.10           │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ 人工审核界面                                          │
│                                                     │
│ 左侧：原文（高亮标注问题）                             │
│ 右侧：知识库对照证据（原文引用 + 出处）                 │
│                                                     │
│ 操作：                                                │
│ · ✅ 通过（AI 判断正确）                               │
│ · ❌ 驳回（AI 判断有误）                               │
│ · ✏️ 修改（AI 判断部分正确）                           │
│ · 添加备注                                            │
│                                                     │
│ 审核结果持久化到 SQLite                               │
└─────────────────────────────────────────────────────┘
```

#### 3.3.2 规则引擎设计（Python 轻量版）

不使用 Drools（Java 生态过重），用 Python + YAML 实现轻量规则引擎：

**设计原则**：
- 规则代码与规则数据分离：代码负责执行逻辑，数据定义具体内容
- YAML 格式，非技术人员可直接编辑规则数据
- 严重级别分层（critical / high / medium / low），支持按场景启用/禁用特定规则
- 规则来源可追溯，支持审计和合规要求
- 热更新：修改 YAML 后无需重启服务，下次校验自动生效

**规则定义**（YAML 格式，与代码分离）：

```python
# 规则引擎加载器
rules:
  - id: compatibility_contravention
    name: "配伍禁忌"
    severity: critical
    description: "检测中药材之间的配伍禁忌关系"
    source: "可追溯至规则来源文献"
    data_file: "rules/compatibility_contraventions.yaml"
    
  - id: dosage_limit
    name: "剂量限制"
    severity: high
    description: "检测药材用量是否超出安全范围"
    source: "药典/古籍"
    data_file: "rules/dosage_limits.yaml"
    
  - id: contraindication
    name: "禁忌症"
    severity: high
    description: "检测是否存在特定人群或病证的禁忌"
    source: "药典/古籍/临床指南"
    data_file: "rules/contraindications.yaml"
    
  - id: regulatory_compliance
    name: "法规合规"
    severity: high
    description: "检测是否符合现行法规要求"
    source: "药典/法规"
    data_file: "rules/regulatory_rules.yaml"

# 规则执行引擎
def check_rules(text, extracted_entities, template_id):
    """
    根据质检模板加载对应规则集，逐条校验
    extracted_entities: 从输入文本中提取的实体列表
    template_id: 质检模板ID，决定启用哪些规则
    """
    # 1. 加载模板对应的规则集
    active_rules = load_rules_for_template(template_id)
    
    # 2. 逐条规则校验
    violations = []
    for rule in active_rules:
        result = rule.check(extracted_entities)
        if result.violated:
            violations.append(result)
    
    # 3. 返回违规列表（包含规则来源、严重级别、建议）
    return violations
```

## 九、关键技术原理

### 9.1 为什么不是简单分词 + 向量搜索？

传统 RAG 的致命缺陷：
1. **固定大小分块**破坏语义完整性（一个方剂被切到两个 chunk 里）
2. **单一检索路径**丢失精确匹配能力（"桂枝三两"这种精确术语搜不到）
3. **无重排机制**导致低质量结果进入 LLM 上下文
4. **分块后丢失全局**LLM 看不到整篇文章的逻辑脉络
5. **古文"上下文极强"**，断章取义会完全误解原意
6. **没有关系建模**无法回答"桂枝汤中哪些药材与藜芦相畏？"

### 9.2 本方案的核心优势

| 优势 | 说明 |
|------|------|
| **智能分块** | 按医学逻辑分，保持方剂/病证完整性 |
| **KG-RAG 增强** | 向量 + 图谱 + 全文三路召回，顶会论文验证提升 10-18% |
| **云端重排** | Cross-Encoder 精排，过滤噪声 |
| **长窗口全量注入** | 找到相关文档后，整篇送 LLM 深度理解 |
| **实体感知** | 知识图谱保证专有名词精确匹配 |
| **确定性守卫** | 十八反/十九畏走规则引擎，LLM 不犯错 |
| **多模型投票** | 争议内容双模型交叉判断，降低误判 |
| **零本地模型** | 全部云端 API，无 GPU 依赖，开箱即用 |

### 9.3 百万 Token 能力的利用方式

```
传统 RAG:
  查询 → 检索 5 个 chunk（~2K tokens）→ LLM 回答
  ↑ 信息碎片化，缺乏全局理解，古文极易误解

KG-RAG 本方案:
  查询 → 智能路由 → 三路召回（向量+图谱+全文）→ 重排
       → 整篇 Parent 文档注入 LLM（50K-500K tokens）
       → LLM 在完整上下文中深度理解
  ↑ 保留完整上下文 + 精确关系 + 深度推理
```

**实际效果差异**：
- 传统 RAG：检索到"桂枝汤"的 3 个碎片 chunk → LLM 只知道组成
- 本方案：注入整篇《伤寒论》中桂枝汤相关章节 → LLM 知道组成 + 适应症 + 禁忌 + 加减法 + 煎服法 + 变方 + 配伍禁忌
