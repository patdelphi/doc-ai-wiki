# UI 重构设计方案（dev）

> 版本：v1.0
> 日期：2026-05-08
> 适用分支：`dev`
> 说明：本文档用于指导当前项目 UI 重构，先统一设计规则，再按模块逐步落地，避免一次性大改导致回归。

---

## 一、目标

本轮 UI 重构聚焦以下目标：

- 提升页面信息层次，降低当前多层嵌套和视觉噪音
- 统一各标签页布局骨架，减少“每页一套规则”的割裂感
- 保留现有业务流程与数据链路，优先做结构和呈现优化
- 让导出、详情、结果反馈、操作按钮形成稳定的一致模式
- 为后续继续逐页演进提供可复用的样式和组件组织规则

本轮明确不做以下事项：

- 不重写后端服务逻辑
- 不改变数据库结构
- 不新增高风险交互依赖
- 不一次性推翻全部页面后再重建

---

## 二、现状判断

当前 UI 主体集中在 `src/ui/pages.py`，存在以下问题：

- 页面布局、组件拼装、样式定义耦合在单文件中，维护成本高
- 说明区、结果区、详情区存在重复包裹，形成多层卡片嵌套
- 页面之间的标题、帮助、动作、反馈位置不统一
- 列表、详情、导出、操作之间的主次关系不够稳定
- CSS 已积累较多针对性补丁，后续继续叠加会让结构更脆弱

同时，`src/ui/viewmodels.py` 已形成相对稳定的展示格式化层，说明当前系统适合采用“先统一布局协议，再逐页替换”的策略，而不是直接重做业务模块。

---

## 三、设计方向

### 3.1 视觉方向

采用“冷静、专业、轻编辑化”的知识工作台风格：

- 基调：克制、清晰、可信，不做花哨或强装饰化设计
- 视觉关键词：秩序、留白、弱边框、轻层次、明确焦点
- 动效原则：只保留轻量过渡，不引入复杂动画
- 目标感受：像一个稳定的专业工作台，而不是营销落地页

### 3.2 与 `frontend-design` skill 的结合方式

在本项目中，`frontend-design` 不用于做强风格化网页，而用于以下约束：

- 保持明确的设计方向，不做默认 Gradio 拼装感
- 统一字体层级、间距节奏、强调色与状态色
- 强化信息编排和视觉层次，而不是堆叠更多面板
- 对每个页面保留一个清晰记忆点，但不破坏整体统一性

---

## 四、全局设计规范

### 4.1 布局规范

- 一行最多左右两列，不允许三列及以上主内容并排
- 主页面遵循“顶部输入/筛选 + 中部主工作区 + 底部辅助区”结构
- 列表区和详情区固定左右分栏，不交叉穿插
- 操作按钮与操作结果必须在同一功能区内闭环展示
- 说明内容优先并入功能区，不单独再包一层冗余说明卡

### 4.2 信息层级规范

- 页面标题区只负责当前页用途、关键提示、少量约束说明
- 列表组件只负责选择和概览，不承载大段正文
- 详情组件只负责当前焦点对象，不同时承担说明职责
- 摘要区只显示关键指标和状态，不堆砌长段文字
- 导出区只放下载动作和下载结果，不混放业务说明

### 4.3 视觉规范

- 背景保持浅色中性基底，局部用弱对比色分层
- 卡片能少则少，优先使用留白、边框、标题分组建立层次
- 统一圆角、边框透明度、阴影强度，避免每块风格不同
- 标题、正文、辅助说明分别固定字号和行高层级
- 强调色聚焦在当前主流程，不允许同一页面出现多种抢眼强调色

### 4.4 交互规范

- 默认首屏只显示必要信息，避免页面加载时灌入过多内容
- 翻页、切换、点选后的反馈位置固定，减少用户视线跳跃
- 空状态、未开始状态、执行中状态、完成状态的呈现方式统一
- 危险动作保持明显区分，但不扩大视觉噪音
- 所有下载结果继续沿用“按钮在上、结果在下、长链接自动折行”的模式

---

## 五、技术落地原则

### 5.1 页面组织原则

后续重构按以下职责边界推进：

- `pages.py`：保留页面装配、事件绑定、组件树定义
- `viewmodels.py`：继续负责摘要卡、详情块、帮助块、结果块的 HTML 格式化
- `UI_CSS`：先做分区整理，再逐步提炼为页面级规则，减少散乱补丁

### 5.2 重构方式

- 先统一布局骨架，再处理细节样式
- 先改结构，再补精确 CSS
- 每完成一个模块，立刻补或改对应 UI 测试
- 每一步只做可回归验证的小改动，避免跨多个页面混改

### 5.3 测试与验收原则

- 结构调整后优先更新 `tests/unit/test_ui.py`
- 保证现有主要 `elem_id` 在必要情况下保持稳定
- 若需要新增结构节点，补充最小必要断言
- 每完成一个模块至少执行一次聚焦 UI 单测与诊断检查

## 六、模块设计方案

### 6.1 AI 质检

定位：主工作台，作为整体 UI 的视觉基线。

改造重点：

- 收紧顶部输入区、模板区、执行摘要区之间的垂直节奏
- 强化“Claim 列表 -> Claim 详情 -> 证据列表 -> 历史记录”的主线顺序
- 历史区与导出区保持独立，但视觉上归入同一层级
- 效果评测作为次级能力，默认保持折叠，不干扰主流程

### 6.2 人工审核

定位：以“待处理 Claim 审核”为中心的决策页。

改造重点：

- 将筛选、待处理、已处理形成稳定的上半区结构
- 将证据区、当前 Claim 详情、审核动作区形成清晰主工作区
- 历史审核记录下沉为辅助回看区，不抢占主路径
- 审核动作、备注、结果反馈形成单列闭环

### 6.3 知识库管理

定位：以文档为中心的维护页。

改造重点：

- 顶部只保留知识库切换、页用途说明和关键摘要
- 当前文档详情作为左侧主焦点，数据库统计作为右侧辅助概览
- 文档列表与分页保持单独区域，不与操作区混叠
- “入库质检”作为扩展能力保留折叠，但内部仍遵循两列上限

### 6.4 知识库检索

定位：以“检索输入 -> 结果列表 -> 原文详情 -> 导出”组成的轻工作流页面。

改造重点：

- 顶部输入区更紧凑，帮助区更短更聚焦
- 结果列表和详情区保持稳定双栏结构
- 结果摘要卡不重复解释检索规则，只显示当前结果概览
- 导出区保持页面底部独立闭环

### 6.5 功能设置

定位：配置管理页，强调稳定和可读。

改造重点：

- 模板管理和知识库管理采用相同的信息结构语言
- 表单分组延续“基础信息 / 策略 / Prompt / 操作”结构
- 列表区、详情区、表单区、结果区的间距和宽度统一
- 危险操作保持明显确认，不通过额外复杂样式制造负担

---

## 七、执行顺序

建议按以下顺序逐模块落地：

1. 先整理全局样式规则与公共布局约束
2. 再优化 `AI 质检`，作为基线页
3. 然后优化 `人工审核`
4. 再优化 `知识库管理`
5. 然后优化 `知识库检索`
6. 最后优化 `功能设置`
7. 完成后再做一次全局样式清理与回归测试

---

## 八、阶段验收标准

- 任意页面主内容都不出现三列并排
- 冗余说明卡明显减少，主流程更连续
- 列表、详情、操作、结果在各页面中的位置规律一致
- 样式规则不再继续无序膨胀，新增 CSS 有明确归属
- `tests/unit/test_ui.py` 能覆盖关键结构调整
- 页面优化以 `dev` 为主线逐步推进，不影响当前主线分支
